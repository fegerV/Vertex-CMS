# Versioning

## Общий подход

VertexCMS использует Semantic Versioning в формате `MAJOR.MINOR.PATCH`.

Пример:

```txt
0.1.0
0.2.0
1.0.0
1.1.3
```

До версии `1.0.0` API и внутренняя архитектура могут меняться быстрее, но breaking changes всё равно должны быть явно описаны в release notes.

## Версии ядра

`MAJOR` увеличивается, если:

- меняется публичный API несовместимым образом;
- ломается совместимость модулей;
- требуется ручная миграция данных;
- удаляется публичный contract, helper, event или route.

`MINOR` увеличивается, если:

- добавляются новые функции;
- добавляются новые API endpoints без поломки старых;
- добавляются новые настройки;
- добавляются новые модули ядра;
- добавляются новые builder blocks.

`PATCH` увеличивается, если:

- исправляются баги;
- улучшается производительность;
- исправляется безопасность без изменения публичного контракта;
- обновляется документация;
- добавляются тесты.

## Каналы релизов

- `dev` - активная разработка.
- `alpha` - функция доступна для ранней проверки.
- `beta` - функция почти готова, возможны изменения деталей.
- `rc` - release candidate.
- `stable` - стабильный релиз.

Примеры:

```txt
0.2.0-alpha.1
0.2.0-beta.1
1.0.0-rc.1
1.0.0
```

## API versioning

API версионируется отдельно через URL prefix:

```txt
/api/v1
/api/v2
```

Правила:

- `v1` нельзя ломать в patch/minor-релизах ядра.
- Новые поля можно добавлять без новой версии API.
- Удаление поля, изменение типа поля или изменение смысла ошибки требует новой major-версии API.
- Deprecated endpoints должны жить минимум один minor-релиз после объявления.
- API errors должны иметь стабильную структуру.

Базовый формат успешного ответа:

```json
{
  "data": {},
  "meta": {
    "api_version": "v1"
  }
}
```

Базовый формат ошибки:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Validation failed.",
    "details": {}
  }
}
```

## Database versioning

Миграции являются частью версии ядра.

Правила:

- Миграции должны быть обратимыми, если это реально безопасно.
- destructive migrations требуют upgrade note.
- переименование колонок должно сопровождаться миграцией данных.
- seeders не должны удалять пользовательские данные.
- installer должен запускать актуальный набор миграций для новой установки.

## Module versioning

Каждый модуль должен иметь собственную версию и совместимость с ядром.

Пример metadata:

```json
{
  "name": "SEO",
  "slug": "seo",
  "version": "0.1.0",
  "core_constraint": "^0.1"
}
```

Правила:

- Core-модули версионируются вместе с ядром.
- Marketplace-модули в будущем версионируются отдельно.
- Модуль не должен активироваться, если его `core_constraint` не совпадает с текущей версией ядра.

## Builder schema versioning

Страницы хранятся как JSON, поэтому schema builder тоже должна иметь версию.

Пример:

```json
{
  "version": "1.0",
  "layout": "default",
  "settings": {},
  "sections": []
}
```

Правила:

- Renderer обязан поддерживать текущую schema version.
- Миграция builder JSON должна быть отдельным сервисом.
- Неизвестные блоки не должны ломать публичную страницу.
- Удаление block type требует миграции или fallback renderer.

## Release checklist

- Обновлена версия в `config/vertex.php` или `.env.example`.
- Обновлены release notes.
- Обновлены docs при изменении поведения.
- Пройдены миграции на чистой базе.
- Пройдены миграции на базе предыдущей версии.
- Пройдены smoke tests installer, auth, pages, media, SEO, cache.
- Проверена совместимость API.
- Проверены permissions для новых действий.
